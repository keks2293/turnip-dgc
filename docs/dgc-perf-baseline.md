# Базовая линия таймингов DGC (A740, 26.11.2026)

До этой точки про DGC в этом дереве нельзя было сказать ничего
количественного: проверок «правильно» было двенадцать, проверок «быстро» —
ноль. `probe19` поставил первую базовую линию, и она хуже ожиданий. Числа
нужны, чтобы каждая следующая оптимизация измерялась против чего-то, а не
«на глаз».

Драйвер в обоих прогонах: `Turnip Adreno (TM) 740`, `Mesa 27.0.0-devel`,
сборка `build/out-star` (sha `libvulkan_freedreno.so` = `8326fa90fda3fb37…`,
та же, на которой 25.11 шёл прогон игры).

## Что именно меряется

Один и тот же результат ставится двумя способами:

* `dgc` — layout на N последовательностей и один `vkCmdExecuteGeneratedCommandsEXT`;
* `manual` — N × (`vkCmdPushConstants` + `vkCmdDraw[Indexed]`), то есть цикл,
  которым vkd3d исполняет `ExecuteIndirect`, когда DGC нет.

Три варианта — формы, которые умеет попросить vkd3d: `{DRAW}` и
`{PUSH_CONSTANT 16B, DRAW}` (два токена подписи `D3D12ExecuteIndirect`:
`CONSTANT_BUFFER_VIEW` + `DRAW`), плюс `{INDEX_BUFFER(DXGI), DRAW_INDEXED}` —
то, ради чего реализован DXGI-режим входных данных. Какие подписи конкретно у
Starfield, пробой не установлено: в журналах прогона нет ни одной строки
`dgc:`, `dgcdump` в игре не включался. Геометрия, пайплайн и состояние в обоих
путях одни и те же, поэтому разница — только в способе поставить команды.

Меряется медиана по 7–25 прогонам (не среднее: одна страница, вытесненная
подкачкой, сдвигает среднее больше, чем сам эффект):

* `inner` — CPU-время самой постановки (`execute` против цикла дроу);
* `rec` — CPU-время записи всего командного буфера;
* `total` — запись + submit + ожидание fence, то есть полный кадр;
* `Δ/seq` — предельная стоимость одной последовательности (`N=1` против `Nmax`).

Readback в стенде (`end_renderpass` копирует 512×256) в замерных прогонах
выключен сознательно — фиксированное копирование съедает кадр из одного дроу.
Картинка проверяется отдельными verify-прогонами: 6 проверок, оба пути на всех
трёх вариантах рисуют (`probe19: 6 checks, 0 fail`).

Повторить:

```

VK_DRIVER_FILES=/var/home/armada/opencode/build/out-star/freedreno_icd.json ./probe19
```

## Что из этого следует

1. **Фиксированная стоимость одного вызова — 33–43 мкс CPU, и она почти не
   зависит от N.** `draw`: 42.7 → 36.8 → 36.6 при N = 1/8/64, и только при
   N = 512 вырастает до 48–58. Для сравнения: один `vkCmdDraw` в том же
   прогоне — 0.73 мкс. Один вызов нашего DGC стоит как 50–60 обычных дроу.
   При 60 Гц это 2–2.5% кадра на *один* вызов, а Starfield за игру делает их
   много.
2. **Предельная стоимость последовательности — 0.011–0.050 мкс** против
   0.028–0.200 мкс у цикла. Но выигрыш целиком лежит в push-константах: у
   `draw` и `indexed` это те же самые числа, что и у цикла (0.011–0.033 против
   0.025–0.030), а в `pc_draw` DGC в 3.4–4.2 раза дешевле, потому что цикл
   платит отдельным `vkCmdPushConstants` на каждую последовательность. То
   есть транслятор сам по себе быстрый и одновременно ничуть не быстрее
   наивного цикла; весь проигрыш — в том, что делается *на вызов*.
3. **По полному кадру DGC проигрывает при любом N и в обоих режимах.**
   Уже при N = 1 (`tiny`): 123–131 мкс против 60–66 мкс, то есть ~65 мкс
   лишней GPU-работы на вызов сверх CPU-ных 35–40. При N = 512 (`tiny`,
   `indexed`): 1960 мкс против 191 мкс. Это не отменится оптимизацией CPU:
   препроцесс-диспатч, запись потока в память, ожидание, пока CP этот поток
   увидит, плюс `CP_INDIRECT_BUFFER` внутри render pass — на binning-архитектуре
   turnip играет всю цепочку дважды (binning и rendering).
4. **Пересечение по CPU — около N ≈ 400** (`inner/x` = 1.55 при N = 512 на
   `pc_draw`, и 0.26–0.32 у `draw`/`indexed` даже при N = 512). По полному
   кадру пересечения нет до N = 512 ни в одном варианте.

Последние две цифры — про `total` в `fat`: там `indexed/128` дал `total/x`
= 1.76 (DGC быстрее), а в первом прогоне те же измерения дали 0.67. В
GPU-связанном режиме `total` меряет не постановку, а очередь на GPU, и обе
величины в нём гуляют в обе стороны; выводы ниже опираются на `inner` и на
`tiny`-режим, где CPU свободен.

**Вывод, который надо уметь вслух сказать: в текущем виде расширение на этом
устройстве — убыток.** Объявлять его с такими числами нельзя, и «сделаем
`VERTEX_BUFFER`, и будет полный набор» эту проблему не решает: VB стоит ~120
строк, а убыток — 1.0–1.8 мс кадра на одном вызове с 512 последовательностями
(1922 мкс против 933 мкс на `pc_draw`).

## Приоритеты, которые из этого получаются

1. **Атрибуция фиксированных 35–40 мкс.** Кандидаты в `tu_dgc_execute`:
   `tu_bo_init_new` на каждый вызов (GEM-аллокация), `tu_cs_reloc_and_patch_cs`
   по списку патчей, поиск препроцесс-пайплайна, запись GPU-дескриптора
   layout'а. Это мерится прогоном с таймерами по фазам под `TU_DEBUG`; без
   него оптимизировать некуда.
2. **Разделить Preprocess и Execute.** Сейчас `isPreprocessed` игнорируется,
   вся работа попадает внутрь render pass, хотя приложение могло попросить
   сделать её раньше. Правка назрела независимо от замеров.
3. **Нативный путь для layout'ов без PC/SI/IB** — `CP_DRAW_INDIRECT_MULTI` с
   `OPCODE=INDIRECT_OP_INDIRECT_COUNT[_INDEXED]`, `INDIRECT = seq_iova + offset`,
   `STRIDE = indirectStride`, `INDIRECT_COUNT = &sequencesCount`, `DST_OFF` под
   `SEQUENCE_INDEX`: нет препроцесса, нет потока в памяти, нет ожидания CP, и
   попутно честный `deviceGeneratedCommandsMultiDrawIndirectCount = true`.
   Варианты `draw` и `indexed` из таблицы — ровно этот случай.
4. `VERTEX_BUFFER` — не оптимизация, а условие законности объявления; его
   имеет смысл делать только после того, как пункты 1–3 дали цифру лучше
   таблицы выше. Иначе мы получим полный набор токенов, который медленнее
   цикла vkd3d.

## Explicit preprocess (probe21/probe23, 2026-11-26)

После фикса explicit preprocess (`1d7c83646a3`, `5636aa45f14`, `17be3c1544c`) добавлены probes:

- `probe20`: smoke correctness для `EXPLICIT_PREPROCESS_BIT` + `isPreprocessed`.
- `probe21`: perf compare `unpreprocessed execute` / `preprocess once + preprocessed execute` / manual CPU loop на explicit-preprocess layout.
- `probe23`: `preprocess once + M preprocessed executes` в одном cmd/RP.

A740, `build/out-star`, tiny GPU-idle, probe21 N=512 median:

| variant | unpre inner/rec/total us | pre inner/rec/total us | manual inner/rec/total us | pre/unpre total | manual/pre total |
|---|---:|---:|---:|---:|---:|
| draw | 1.56 / 3.54 / 868.15 | 0.99 / 2.97 / 352.12 | 18.23 / 27.24 / 230.56 | 0.41x | 0.65x |
| pc_draw | 3.02 / 6.46 / 1787.33 | 0.99 / 3.85 / 364.41 | 79.58 / 83.90 / 448.27 | 0.20x | 1.23x |
| indexed | 2.03 / 4.74 / 1385.99 | 1.04 / 3.80 / 388.48 | 17.29 / 20.47 / 194.68 | 0.28x | 0.50x |

probe21 fat, N=512 (separate run): `pc_draw` pre total `371.92us` vs manual `449.00us`; `draw`/`indexed` still behind manual total.

probe23, N=512, M=32, preprocess once:

| variant | exec-many inner/total us | per-exec inner/total us |
|---|---:|---:|
| draw | 15.99 / 10138.86 | 0.50 / 316.84 |
| pc_draw | 13.85 / 9867.20 | 0.43 / 308.35 |

Вывод: preprocessed execute убирает большую часть DGC overhead; CPU inner cost амортизируется, но fixed submit/GPU/state/IB overhead остаётся. PC-heavy path выигрывает сильнее всего. Fast path для explicit-preprocess unpreprocessed execute пробовался, но вызывал регресс/краш probe20/probe21 и откачен.

## Оговорки к цифрам

* Пробы — нативные aarch64. В игре вызовы vkd3d идут через wine + FEX, то
  есть `man inner` в жизни дороже, чем 0.028–0.200 мкс, и пересечение по CPU
  наступает раньше. Насколько раньше — не измерено; фиксированные 35–40 мкс
  от этого не меняются, они целиком внутри драйвера.
* Один поток, одна очередь, без параллельной загрузки шейдеров; в игре vkd3d
  компилирует шейдеры параллельно, и там обе величины хуже.
* В `dgc inner` входит проверка layout'а и подготовка состояния — в
  manual-пути аналога нет, потому что там состояние уже зашито в команды.
  Это завышает `dgc inner` ровно на фиксированную часть, то есть пункт 1
  списка приоритетов получает из этих чисел верхнюю оценку.
* Разброс между двумя прогонами одной и той же сборки — до 1.5× на
  `Δ/seq` (`indexed`: 0.028 и 0.050) и единицы мкс на фиксированной части.
  Это предел, с которым стоит сравнивать будущие оптимизации: всё, что
  меньше 10 мкс на вызов, этой пробой не доказать.
